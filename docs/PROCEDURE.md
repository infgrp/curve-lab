# 곡선 찾기 실험실 — VS Code + Claude Code 작업 절차

이 절차서는 사람(사용자)이 할 일과 Claude Code에게 줄 지시를 단계별로 나눈 것이다. 각 Phase는 **계획 → 구현 → 검증 → 커밋**의 같은 순환을 따른다.

---

## 공통 작업 규칙 (모든 Phase에 적용)

1. **계획 먼저.** Phase를 시작할 때마다 Claude Code를 plan 모드로 두고(터미널 CLI에서는 Shift+Tab으로 전환, VS Code 확장에서는 모드 선택 메뉴) 계획을 받는다. 계획을 읽고 승인한 뒤에 구현하게 한다.
2. **문맥 비우기.** Phase가 끝나 커밋한 뒤에는 `/clear`로 대화를 비운다. 규칙은 CLAUDE.md에, 명세는 SPEC.md에 있으므로 대화 기록이 없어도 일관성이 유지된다.
3. **diff를 직접 읽기.** 특히 `tests/` 아래 변경은 반드시 확인한다. 테스트 기대값이 바뀌었다면 왜 바뀌었는지 물어본다.
4. **스스로 검증하게 하기.** 지시 끝에 "`npm test`와 `npm run typecheck`를 실행해 결과를 보여 줘"를 붙인다.
5. **커밋은 Phase 단위.** 아래 각 Phase의 커밋 메시지 예시를 쓴다.

---

## Phase 0. 환경 준비 (사람이 직접)

1. 설치: Git, Node.js LTS(24 이상 권장), VS Code.
2. VS Code 확장 마켓플레이스에서 Anthropic의 **Claude Code** 확장을 설치하고 로그인한다. (확장 대신 VS Code 내장 터미널에서 `claude`를 실행해도 같은 작업을 할 수 있다.)
3. 작업 폴더를 만들고 이 문서 묶음을 복사한다.
   ```
   curve-lab/
   ├── CLAUDE.md
   ├── docs/SPEC.md
   ├── docs/PROCEDURE.md
   └── reference/overfit_experiment.py
   ```
4. VS Code에서 `curve-lab` 폴더를 열고 `git init` 후 첫 커밋을 한다.

```bash
git init && git add . && git commit -m "docs: 명세와 작업 절차 추가"
```

**완료 기준:** VS Code에서 Claude Code 패널이 열리고, "CLAUDE.md를 요약해 줘"라고 했을 때 프로젝트 규칙을 정확히 요약한다.

## Phase 1. 프로젝트 골격

**Claude Code 지시:**
> CLAUDE.md와 docs/SPEC.md를 읽어. Vite의 vanilla-ts 템플릿으로 현재 폴더에 프로젝트를 만들되, 기존 문서 파일은 건드리지 마. TypeScript strict 모드, Vitest 설정, 스크립트(dev, build, test, typecheck)를 추가하고, CLAUDE.md의 디렉터리 규칙대로 src/core, src/ui, tests, scripts 폴더를 만들어. 템플릿의 예제 코드는 지우고, 빈 화면에 "곡선 찾기 실험실" 제목만 나오게 해. 마지막에 npm test(빈 테스트 1개)와 typecheck, build를 실행해 결과를 보여 줘.

**사람이 확인:** `npm run dev`로 브라우저에서 제목이 보이는지, `package.json`에 원격 CDN이나 불필요한 의존성이 없는지 확인한다.

커밋: `chore: Vite+TS+Vitest 골격`

## Phase 2. 수학 핵심부 (`src/core`) — UI 없이 테스트 우선

이 Phase가 전체 품질을 좌우한다. 하나의 지시로 몰아서 하지 말고 아래 2-1~2-5를 순서대로 진행한다.

**2-1 시드 난수와 데이터**
> SPEC 0절을 구현해. src/core/rng.ts(mulberry32 같은 시드 고정 난수와 Box–Muller 정규난수)와 src/core/data.ts(학습 점 12개, 검증 점 40개 생성). 테스트를 먼저 작성해: 같은 시드면 같은 데이터, 학습 점이 [-1,1]의 양 끝 근처를 덮음, 검증 점이 학습 점 x 범위 안에 있음, 정규난수 10만 개의 표본평균과 표본분산이 각각 0과 1에 가까움(허용오차는 표준오차의 4배로 근거를 주석에 적기).

**2-2 직선 모델**
> SPEC 1단계의 core 부분을 구현해. src/core/linear.ts에 손실, 기울기, 닫힌 해, 헤세 행렬의 최대 고유값, 경사하강 한 스텝을 넣어. SPEC에 적힌 테스트 4개를 먼저 작성하고 통과시켜.

**2-3 공통 도구: 유한차분 검사기**
> tests/helpers/gradcheck.ts를 만들어. 매개변수 벡터와 손실 함수를 받아 중앙차분(h=1e-6)으로 수치 기울기를 계산하고, 해석적 기울기와의 상대오차를 반환해. 2-2의 기울기 테스트도 이 도구를 쓰도록 바꿔.

**2-4 꺾은선 모델**
> SPEC 2단계의 core 부분을 구현해(src/core/hinge.ts). 특히 ReLU 신경망 → 꺾은선 모델 변환 함수를 만들고, SPEC의 동치성 테스트를 작성해. 유한차분 검사는 꺾이는 점에서 1e-3 이상 떨어진 x만 쓰도록 데이터를 고르고, 그 이유를 주석에 남겨.

**2-5 신경망과 Adam**
> SPEC 3단계의 core 부분을 구현해(src/core/mlp.ts, src/core/optim.ts). Float64Array를 쓰고, 매 epoch마다 메모리를 새로 할당하지 마. SPEC의 테스트 4개를 작성하고 통과시켜. Adam 한 스텝 테스트는 매개변수 2개짜리 장난감 문제로 기대값을 손으로 계산해서 주석에 계산 과정을 적어.

**사람이 확인:** 각 테스트가 실제로 무엇을 비교하는지 읽어 본다. 특히 "허용오차가 너무 느슨해서 틀린 구현도 통과할 수 있는가?"를 따진다. 의심되면 Claude에게 "기울기 부호를 일부러 바꾼 구현이 이 테스트에서 실패하는지 확인해 줘"라고 시켜 본다(돌연변이 검사). 확인이 끝나면 변경을 되돌리게 한다.

커밋: 2-1~2-5마다 하나씩. 예: `feat(core): 꺾은선 모델과 ReLU 동치성 테스트`

## Phase 3. 그리기 공통부 (`src/ui/plot.ts`)

> 수학 좌표계(x∈[-1.2,1.2], y 범위는 인자)와 캔버스 픽셀 좌표의 변환, 축, 점(원/다이아몬드), 곡선(함수를 받아 픽셀 단위로 샘플링), 잔차 선분, 등고선(격자값과 등고선 수준을 받아 marching squares로 그림)을 그리는 모듈을 만들어. devicePixelRatio를 반영해 선명하게 그리고, 창 크기가 바뀌면 다시 그려. 확인용 임시 페이지(dev 전용)에서 사인 곡선, 점, 등고선이 나오게 해.

**사람이 확인:** 키오스크와 같은 해상도(1920×1080)로 브라우저를 맞추고 선명도와 글자 크기를 본다.

커밋: `feat(ui): 캔버스 그리기 모듈`

---

## Phase 4. 1단계 화면

> SPEC 1단계 UI를 구현해(src/ui/stage1.ts). 슬라이더 두 개, 잔차 선분, 손실 표시, 오른쪽 손실 등고선과 현재 위치, "기계에게 맡기기"와 학습률 3개 선택지, 발산 시 경로가 화면 밖으로 나가도 앱이 멈추지 않게(NaN/Infinity 처리) 해 줘. 안내 문구 초안도 써 줘. 문구는 내가 검토할 테니 src/ui/text.ko.ts에 모아 둬.

**사람이 확인:**
- 슬라이더로 손실을 줄여 간 위치가 등고선의 골짜기와 일치하는가?
- 적당한 학습률에서 경로가 닫힌 해(최솟점)에 도달하는가? 너무 큰 학습률에서 실제로 발산하는가?
- 손가락으로 슬라이더를 조작하기 편한가(터치 모니터나 브라우저 개발자 도구의 터치 에뮬레이션으로 확인)?
- `text.ko.ts`의 문구를 직접 고친다. 수학적으로 부정확한 비유가 없는지 본다.

커밋: `feat(stage1): 직선 맞추기 화면`

## Phase 5. 2단계 화면

> SPEC 2단계 UI를 구현해(src/ui/stage2.ts). 1단계에서 찾은 (a,b)를 이어받아. 꺾이는 점 손잡이 3개(좌우 드래그=t, 상하 드래그=s, Pointer Events, 최소 48px), 성분별 옅은 선과 합의 굵은 선, "기계에게 맡기기", 기울기가 0인 뉴런에 "쉬고 있어요" 표시. 손잡이가 겹치면 마지막에 잡은 것이 위로 오게 해.

**사람이 확인:** 꺾이는 점을 학습 점 오른쪽 끝 너머로 보낸 뒤 "기계에게 맡기기"를 눌러, 그 뉴런이 실제로 움직이지 않고 표시가 뜨는지 본다.

커밋: `feat(stage2): 꺾은선 더하기 화면`

## Phase 6. 3단계 화면과 과적합 재현 실험

**6-1 실험 재현 (UI보다 먼저)**
> scripts/experiment-overfit.ts를 만들어 reference/overfit_experiment.py와 같은 실험을 src/core 코드로 재현해(시드 20개, 뉴런 1,2,4,8,16,64, 20000 epoch, 학습/검증 MSE의 평균과 중앙값 표). 실행 결과를 SPEC 0절의 Python 결과와 비교해서 보고해. 난수 생성기가 달라 숫자가 같지는 않을 테니, "작음→적당→큼"의 U자형 경향이 유지되는지를 기준으로 판단해.

여기서 U자형이 재현되지 않으면 UI로 넘어가지 않는다. 학습 점 수와 σ를 조정하는 실험을 더 시키고, 결과에 따라 SPEC을 갱신한다.

**6-2 화면**
> SPEC 3단계 UI를 구현해(src/ui/stage3.ts, src/ui/scoreboard.ts). 뉴런 수 선택(2/8/64), 학습 애니메이션(프레임당 epoch 수를 조절해 화면이 끊기지 않게), 학습 손실 그래프, "숨겨진 점 공개", 잡음 하한 기준선, 오늘의 방문자 분포 히스토그램과 뉴런 수별 평균, "다시 해 보기". localStorage는 try/catch로 감싸.

**사람이 확인:**
- 64개 뉴런의 곡선이 눈에 보이게 점마다 꺾이는가? 숫자 차이가 작으므로 이 시각적 차이가 핵심이다.
- 학습 중 다른 버튼을 연타해도 상태가 꼬이지 않는가?
- 키오스크로 쓸 PC(또는 그와 비슷한 저사양 PC)에서 64개 뉴런 학습이 몇 초 걸리는가?

커밋: `feat(stage3): 신경망 학습과 숨겨진 점`

## Phase 7. 전체 흐름과 키오스크 기능

> SPEC 4절을 구현해: 시작 화면, 단계 이동과 건너뛰기, 120초 무입력 초기화, 교사 설정 화면(왼쪽 위 3초 길게 누르기), 기록 CSV 내보내기. 무입력 타이머와 상태 초기화는 단위 테스트 가능하게 시간 함수를 주입받도록 만들어.

> (선택) Playwright로 "시작 → 1단계 슬라이더 조작 → 건너뛰기 → 3단계 학습 → 공개 → 120초 후 초기화" 종단 테스트를 작성해.

커밋: `feat(app): 전체 흐름과 키오스크 기능`

## Phase 8. 점검

1. **코드 검토:** Claude Code에서 `/code-review` 같은 검토 기능을 쓰거나, "src/core 전체를 SPEC과 대조해 불일치를 찾아 줘"라고 지시한다.
2. **오프라인 점검:** 네트워크를 끊고 `npm run build && npx vite preview`로 실행한다. 개발자 도구 Network 탭에 외부 요청이 하나도 없어야 한다.
3. **사용자 시험:** 학생 3~5명과 교사 1~2명에게 안내 없이 체험하게 하고 다음을 기록한다.
   - 단계별 소요 시간
   - 막힌 지점
   - 체험 후 "왜 64개 뉴런이 꼭 가장 좋은 것은 아닌가?"에 답할 수 있는지
4. 결과를 바탕으로 `text.ko.ts`의 문구와 SPEC을 고친다.

---

## Phase 9. 배포 (키오스크 PC)

1. `npm run build`로 만든 `dist/`를 키오스크 PC에 복사한다.
2. 로컬 정적 서버로 띄운다(예: `npx serve dist` 또는 Python `http.server`). `file://`로 직접 열면 ES 모듈 로딩이 막힐 수 있으므로 서버를 쓴다.
3. Chrome을 키오스크 모드로 실행한다(`--kiosk http://localhost:포트`). 부팅할 때 자동 실행되게 설정한다.
4. 기관의 정보보안 규정에 따라 설치 승인 절차를 확인한다. 앱은 외부 통신을 하지 않고 개인정보를 수집하지 않는다는 점을 문서로 남긴다.

## 부록 A. Claude Code와 일할 때 자주 생기는 문제

| 증상 | 대응 |
|---|---|
| 한 번에 여러 Phase를 진행해 버림 | "Phase N만 해. 끝나면 멈추고 보고해"를 지시에 명시한다(CLAUDE.md 규칙 8) |
| 테스트가 실패하자 테스트를 고침 | 되돌리게 하고 "구현을 고쳐. 테스트를 바꿔야 한다면 근거를 먼저 설명해"라고 지시한다 |
| 라이브러리를 추가하려 함 | CLAUDE.md의 스택 규칙을 상기시킨다 |
| 대화가 길어져 이전 결정을 잊음 | 결정 사항을 SPEC에 반영하게 하고 `/clear` |
| 수식 설명이 그럴듯하지만 의심스러움 | "이 주장을 검증하는 테스트나 수치 실험을 만들어 줘"라고 요구한다 |
